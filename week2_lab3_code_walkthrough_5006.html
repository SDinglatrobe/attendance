Part 2: What is npm, really?

npm (Node Package Manager) comes with Node.js. It does two jobs in this project:

  • npm install reads the dependencies in package.json and downloads them into a folder called node_modules. For this app the dependencies are express (the web framework) and qrcode (to draw the QR code). Run it once before starting, and again whenever dependencies change.
  • npm start runs the command in the scripts.start field of package.json. Here that is node server.js, which launches the backend.
# Look at the project's own description of itself
cat package.json

# The key parts you just learned about:
#   "scripts": { "start": "node server.js" }
#   "dependencies": { "express": "^4.18.3", "qrcode": "^1.5.4" }
#   "engines": { "node": ">=18" }

Why node_modules is not on GitHub

The downloaded packages in node_modules are large and can be rebuilt anytime from package.json. So projects do not upload that folder; instead the host (or you) runs npm install to recreate it. That is exactly why Render's build command is npm install.

Part 3: Frontend vs backend — what is the difference here?

Every web app has two sides:

  • The frontend is what the visitor sees and interacts with in the browser: the HTML structure, the CSS styling, the text and buttons. It runs on the user's device.
  • The backend is the program on the server: it decides what each address does, checks the student ID, enforces “one check-in per week”, and saves records. It runs on the server, never in the visitor's browser.

This app is deliberately simple: both the frontend and the backend live in one file, server.js. The backend builds the frontend as HTML text and sends it to the browser. That is why there is no separate folder of HTML files here.

How to tell which is which in server.js

The frontend is inside the pageTemplate(...) function: the <style> block (CSS) and the HTML strings with <h1>, forms and buttons. The backend is the app.get(...) and app.post(...) route handlers and the helper functions that validate IDs, manage weeks, and read/write the records file.

Part 4: Make one small frontend change (font size and text)

Let us change something visible without touching any backend logic. Open server.js in your editor (for example nano):

nano server.js

Change 1 — the heading font size (CSS). Find this line inside the <style> block:

    h1 { font-size: 28px; margin: 0 0 8px; text-align:center; }

Change 28px to something larger, for example 40px:

    h1 { font-size: 40px; margin: 0 0 8px; text-align:center; }

Change 2 — the main heading text (HTML). Find this line in the app.get("/") handler:

      <h1>Attendance Check</h1>

Change the text between the tags (keep the tags exactly as they are):

      <h1>Class Check-In</h1>

Save the file (in nano: Ctrl+O, Enter, then Ctrl+X). Restart the app so the change loads:

# Stop the running app with Ctrl+C in its terminal, then start it again
npm start

# Refresh http://localhost:3000 -- the heading is larger and says "Class Check-In".

Change only what is shown; keep the tags and quotes

Edit the text between <h1> and </h1>, and the number in font-size. Do not delete the tags, the backticks around the HTML, or the surrounding code. If the app fails to start after editing, you very likely removed a quote, a backtick, or a bracket — undo your change and try again carefully.

Why a restart is needed

This backend builds the HTML from the code loaded in memory. Node loads server.js when it starts, so a source change only takes effect after you stop and start the app again. (Tools like nodemon can auto-restart during development, but we keep it manual here.)

Part 5: Test the backend directly with curl

The browser is one way to reach the backend; curl is another. curl sends an HTTP request from the terminal and shows the response, with no browser involved. This lets you test backend routes precisely. Open a second terminal in your VM (leave the app running in the first). Add -i to also see the HTTP status line (200, 400, ...).

About the multi-line commands and the week value

Each command below is shown on multiple lines using a backslash \ at the end of a line, which is how Ubuntu's bash joins lines. If you prefer, a single-line version of each command is given underneath — type it all on one line with no backslash.

The week value is only a demonstration parameter. In the app's default test mode the server uses the current teaching week regardless of the number you send, and it allows one check-in per student for that week. So sending a different week number does not let the same student check in twice.

1) Ask the backend for the check-in page (the frontend HTML it builds):

curl -i http://localhost:3000/

2) Submit a check-in for a real roster student (CSE5006 id 99500001):

# Multi-line form
curl -i -X POST http://localhost:3000/checkin \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "studentId=99500001"

# Single-line form (same thing)
curl -i -X POST http://localhost:3000/checkin -d "studentId=99500001"

Expected: HTTP/1.1 200 OK and a page that says Check-in Successful with the name Adams Isla.

3) Submit the SAME student again — the backend blocks a second check-in:

curl -i -X POST http://localhost:3000/checkin -d "studentId=99500001"

Expected: a page that says Already Submitted.

4) Submit an ID that is not in the roster:

curl -i -X POST http://localhost:3000/checkin -d "studentId=99999999"

Expected: Student Not Found.

5) Submit a badly formatted ID:

curl -i -X POST http://localhost:3000/checkin -d "studentId=abc"

Expected: Invalid Student ID.

You did all of this without a browser, proving the rules live in the backend, not the frontend.

You can also check the other routes:

# The weekly QR page (returns 200 OK and an HTML page with the QR image)
curl -i http://localhost:3000/qr

# The admin page without logging in (returns the admin login page)
curl -i http://localhost:3000/admin

What you are observing

The exact same backend logic ran in Lab 1 (on Render) and Lab 2 (behind Nginx). curl lets you test it in isolation. Real developers use curl constantly to confirm an API behaves correctly before any frontend is finished.

Part 6: See where the backend stored your check-in

The successful check-in from Part 5 was saved by the backend to a file. Look at it:

cat data/attendance.json

You will see your check-in for student 99500001 recorded under the current week, with a timestamp. This is the backend's job: turning a request into stored data. The frontend never does this — it only shows pages.
