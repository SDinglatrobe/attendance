Part 2: Two ideas to hold onto — ports and routing

A port is a numbered doorway into a computer. Many programs run at once because each claims a different number. The web has agreed defaults so browsers know where to knock:

  • Port 80 — plain HTTP. http://... uses it.
  • Port 443 — HTTPS (encrypted). https://... uses it.
  • Port 3000 — what the attendance app uses by default while running.

Routing means deciding what to send for each address. For a static site the web server matches a file on disk. For the Node.js app, the app's own code matches a function (for example app.get("/") and app.post("/checkin")). Hold onto this difference; it explains everything below.

Part 3: Serve the static site with Nginx

Nginx listens on port 80 and sends files from a folder called the web root, which on Ubuntu is /var/www/html.

# Install and start Nginx
sudo apt install nginx -y
sudo systemctl enable nginx
sudo systemctl start nginx
sudo systemctl status nginx --no-pager

# Ask the server, on this machine, for its home page
curl -I http://localhost

Checkpoint

curl -I http://localhost returns HTTP/1.1 200 OK, and opening http://localhost in the VM's browser shows the default Nginx welcome page. If not, Nginx is not running — re-check the systemctl status output.

That welcome page is just the file in the web root. Replace it with your first-website from Lab 1 (your own files, or the example from the Week 1 static-site repository):

# Get your static site from GitHub
git clone https://github.com/YOUR-GITHUB-USERNAME/first-website.git
cd first-website

# Copy your files into the Nginx web root
sudo rm -rf /var/www/html/*
sudo cp -r * /var/www/html/

# Let the web server's user own and read the files
sudo chown -R www-data:www-data /var/www/html
sudo find /var/www/html -type d -exec chmod 755 {} \;
sudo find /var/www/html -type f -exec chmod 644 {} \;

# Test the config, reload, and check
sudo nginx -t
sudo systemctl reload nginx
curl -I http://localhost

What those permission numbers mean

chown www-data makes the web server's user the owner so it may read the files. 755 on folders = owner full control, others may enter and read. 644 on files = owner may edit, others may read. Web files must be readable by the server but not writable by everyone.

Understand the Nginx site configuration

The professional way is to give each site its own config file. Create one (open it in your editor of choice, e.g. nano):

sudo mkdir -p /var/www/first-website
sudo cp -r * /var/www/first-website/
sudo chown -R www-data:www-data /var/www/first-website
sudo nano /etc/nginx/sites-available/first-website

Put this inside, then read the explanation below it:

server {
    listen 80;
    server_name _;

    root /var/www/first-website;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
  • listen 80; — wait for visitors on the public HTTP port.
  • server_name _; — match any host name (fine for an IP/localhost demo).
  • root /var/www/first-website; — the folder to serve files from.
  • index index.html; — the default file for /.
  • try_files $uri $uri/ =404; — the routing rule: try the exact file, then a folder, else return 404.
# Enable this site, disable the default, check, reload
sudo ln -s /etc/nginx/sites-available/first-website /etc/nginx/sites-enabled/first-website
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

Checkpoint

sudo nginx -t prints “syntax is ok” and “test is successful”, and http://localhost now shows your page, not the Nginx default. If nginx -t reports an error, re-open the config file and check for a missing ; or }.

Part 4: The same site with Apache (alternative)

Apache does the same core job. Use it instead of Nginx, not at the same time, because both want port 80. Its web root on Ubuntu is also /var/www/html.

Stop Nginx before starting Apache

Only one program can hold port 80. If Nginx is running from Part 3, stop it first with sudo systemctl stop nginx, otherwise Apache fails to start with “Address already in use”.

# Stop Nginx, then install and start Apache
sudo systemctl stop nginx
sudo apt install apache2 -y
sudo systemctl start apache2
sudo systemctl status apache2 --no-pager

# Copy your static site into the Apache web root
cd ~/first-website
sudo rm -rf /var/www/html/*
sudo cp -r * /var/www/html/
sudo chown -R www-data:www-data /var/www/html

# Reload and test
sudo systemctl reload apache2
curl -I http://localhost

Nginx vs Apache, in one line

Both serve files on port 80. Apache is older and very common in traditional hosting; Nginx is lighter and is also excellent at forwarding traffic to an app (a reverse proxy), which is what we need for Node.js next. For the rest of this lab we use Nginx, so switch back now: sudo systemctl stop apache2 then sudo systemctl start nginx.

Part 5: Run the Node.js attendance app — and why it still needs Nginx

The static site was just files. The attendance app is a program that must keep running to answer visitors. Install Node.js and start the app (from the attendance repository on GitHub):

# Install Node.js and npm
sudo apt install nodejs npm -y
node -v
npm -v

# Get the app and start it
git clone https://github.com/SDinglatrobe/attendance.git
cd attendance
npm install
npm start

It prints that it is listening on port 3000. Open http://localhost:3000 to use it — this is the app routing requests itself. Stop it with Ctrl+C for now.

Why does a Node site still need Nginx? (important)

The app works on port 3000, but real visitors expect a normal address on port 80 (HTTP) or 443 (HTTPS), with no :3000. You could try to run Node directly on port 80, but that is discouraged: ports below 1024 need root privileges (risky), and Node alone does not easily handle HTTPS certificates, efficient static-file serving, compression, or several sites on one machine.

So we put Nginx in front. Nginx listens on the public 80/443, deals with HTTPS, and quietly forwards each request to the app on port 3000. This is a reverse proxy. The visitor sees a clean address; Nginx and Node talk privately behind it. This is the standard professional pattern.

Keep the app alive with PM2

If you close the terminal, npm start stops. A process manager called PM2 keeps it running in the background and restarts it after a reboot.

sudo npm install -g pm2

# Start the app through PM2 using the project's npm start
pm2 start npm --name attendance -- start
pm2 status
pm2 logs attendance

# Make PM2 restart your apps after a reboot
pm2 save
pm2 startup systemd
# Run the command pm2 prints, then run: pm2 save

Checkpoint

pm2 status shows attendance with status online. curl -I http://localhost:3000 returns HTTP/1.1 200 OK. If the status is errored, read pm2 logs attendance.

Put Nginx in front (reverse proxy)
sudo nano /etc/nginx/sites-available/attendance

Put this inside, then read the explanation:

server {
    listen 80;
    server_name _;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
  • proxy_pass http://127.0.0.1:3000; — forward every request to the app on port 3000.
  • The proxy_set_header lines pass the visitor's real host and IP to the app, which reads them via app.set("trust proxy", true) in the code.
# Enable the proxy site, disable the default, check, reload
sudo ln -s /etc/nginx/sites-available/attendance /etc/nginx/sites-enabled/attendance
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

# Now the app is reachable on the normal port 80
curl -I http://localhost

Checkpoint

http://localhost (no :3000) now shows the attendance check-in page. The reverse proxy is working: Nginx on port 80 is forwarding to Node on port 3000.

Part 6: Turn on HTTPS with a TLS certificate you create

HTTPS is HTTP wrapped in TLS encryption. A real public site uses a free trusted certificate (for example from Let's Encrypt), but that needs a real domain name. For local learning we create a self-signed certificate: it encrypts traffic the same way, but because no trusted authority vouches for it, the browser shows a one-time warning. That is expected and fine for practice.

Generate the certificate and its private key in one command:

# Make a folder to hold the certificate and key
sudo mkdir -p /etc/nginx/certs

# Create a self-signed certificate (.crt) and private key (.key), valid 365 days
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/nginx/certs/attendance.key \
  -out /etc/nginx/certs/attendance.crt \
  -subj "/CN=localhost"

What each part of that command means

req -x509 makes a self-signed certificate (not a request to a real authority). -nodes means “no passphrase on the key” so the server can start unattended. -days 365 sets one year of validity. -newkey rsa:2048 creates a fresh 2048-bit key. -keyout and -out are the private key and certificate files. -subj "/CN=localhost" sets the name to localhost for this demo.

You can inspect what you created:

sudo openssl x509 -in /etc/nginx/certs/attendance.crt -noout -subject -dates
Tell Nginx to use HTTPS and redirect HTTP to it
sudo nano /etc/nginx/sites-available/attendance

Replace the file contents with this. It serves HTTPS on 443 and sends plain HTTP on 80 to HTTPS:

server {
    listen 443 ssl;
    server_name localhost;

    ssl_certificate     /etc/nginx/certs/attendance.crt;
    ssl_certificate_key /etc/nginx/certs/attendance.key;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name localhost;
    return 301 https://$host$request_uri;
}
  • listen 443 ssl; — serve encrypted HTTPS on the standard port.
  • ssl_certificate / ssl_certificate_key — the certificate and key you just generated.
  • The second server block listens on 80 and return 301 https://... permanently redirects visitors to HTTPS.
# If the Ubuntu firewall (ufw) is active, allow HTTP and HTTPS
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Check config and reload
sudo nginx -t
sudo systemctl reload nginx

# Test HTTPS locally. -k tells curl to accept the self-signed certificate.
curl -Ik https://localhost

Checkpoint

curl -Ik https://localhost returns HTTP/1.1 200 OK. In the browser, https://localhost shows a warning (because the certificate is self-signed) — choose to proceed, which is safe on your own machine. You then see the attendance app with a padlock in the address bar: it is running over HTTPS, behind Nginx, served from port 3000 underneath.

Self-signed vs trusted

A self-signed certificate encrypts traffic but browsers do not trust it automatically, so they warn. That is correct for local practice. On a real public server with a real domain you would instead run sudo certbot --nginx -d yourdomain.com to get a free certificate browsers trust with no warning.

Local files are kept here

Running on your own machine, the attendance app writes check-ins to data/attendance.json and that file stays on disk — unlike Render's stateless free tier in Lab 1. Permanent storage is a main reason to run your own server.
